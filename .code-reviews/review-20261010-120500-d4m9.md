## Findings

### F1 — MEDIUM — README config example uses a `[list]` table the code does not read
File: `README.md:107-110`
The sample puts `page_size`, `default_estimate_days`, `gantt_weeks` under a
`[list]` table, but the TOML tags are flat top-level keys
(`list_page_size`, `default_estimate_days`, `gantt_weeks`; `config.go:27`). A
user copying the sample gets defaults silently. This change appends the new
`[[harness]]`/`[handoff]` blocks into the same (broken) sample, so the whole
example stays uncopyable. context.md L36/L99 flags the drift but the change did
not fix it.
Fix: correct the sample to the real flat keys (`list_page_size = 10`, …) before
or with the new `[[harness]]`/`[handoff]` block.

### F2 — MEDIUM — FEATURES.md claims a config warning that does not exist
File: `docs/FEATURES.md` config section — "Malformed config falls back to
defaults with a warning."
`config.Load` (config.go:110-149) is silent: no `log`, no stderr write, no
warning path anywhere in the package (verified). issue.md AC9 and plan.md L40
also reference a "warning behavior". The change edited this exact line but kept
the inaccurate clause.
Fix: drop "with a warning" (or implement the warning), and align issue/plan
wording.

### F3 — MEDIUM — planning docs still say the prompt embeds the description
Files: `plan.md:9`, `issue.md:33-36,72-73`
plan.md "Intended outcome" says "hands the task's **description** to the chosen
harness"; issue.md AC4/scope say the payload is
`I need to implement this: <description>`. The shipped prompt deliberately does
**not** embed the description (ADR, behavior.feature L64-67,
`harness_test.go:118`). behavior.feature and ADR were updated; plan.md/issue.md
were not, so the planning set contradicts itself.
Fix: update plan.md L9 and issue.md AC4 to the pointer-based prompt, or mark
them superseded by behavior.feature.

### F4 — LOW — README `binary` comment mis-describes and duplicates `name`
File: `README.md:114-115`
`binary = "opencode"  # optional; listed even when PATH detection misses it` —
the comment describes the entry's listing behavior, not `binary`, and in the
example `binary` equals `name` (redundant). Slightly misleading for readers.
Fix: reword the comment to "optional; executable to look up (defaults to name)".

### F5 — LOW — "the task project's valid statuses" is stronger than the code
Files: `README.md:128`, `docs/FEATURES.md` Ask AI entry
The docs state the prompt lists the task project's statuses unconditionally. In
the TUI, `workflowForProject` falls back to `mergedWorkflow()` when the project
is not loaded (askai_modal.go:78-83); in the CLI, `askStatuses` returns nil
(drops the clause) on a project-lookup error (cli.go). The statuses are not
always the task project's.
Fix: say "the project's workflow when available, otherwise the merged workflow",
or accept the edge and note it.

### F6 — LOW — herdr example depends on `jq` without saying so
File: `README.md:118`, `docs/adr/0001-ask-ai-handoff-contract.md` example
The example pipes through `jq`, an external tool not mentioned as a
requirement; on a machine without `jq` the handoff fails at spawn/exit.
Fix: note `jq` as a prerequisite of that example (or use a jq-free extraction).
