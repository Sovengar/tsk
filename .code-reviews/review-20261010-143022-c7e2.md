## Finding 1 — The `binary` config key never reaches the handoff command

**Title:** `Harness.Binary` is dead for config-declared harnesses: `{{harness}}`
expands to the display *name*, never the binary.
**Why it matters:** bug (misleading public config surface / latent surprise)
**Where:** `internal/harness/harness.go` `declaredHarnesses` (~L86–95),
`internal/cli/cli.go` `selectHarness` (L716–733),
`internal/tui/askai_modal.go` (L53)
**Evidence:** `Binary` is only read by `detectedBuiltins()` (`lookPath(h.Binary)`,
harness.go:78) for the *builtin* registry. For declared entries it is stored and
asserted by tests (`TestDetectConfigOverridesDetectedSameName` checks
`Binary == "opencode-custom"`) but never consumed. The launch path takes only the
display name: `selectHarness` returns `h.Name`, the TUI stores
`m.askAIList[i].Name`, and `Launch`→`ExpandTemplate` substitutes `{{harness}}`
with `shellQuote(harnessName)` (the name). So a user who declares
`[[harness]] name="opencode" binary="/opt/oc/bin/opencode"` and a command
`opencode run {{harness}}` gets `opencode run 'opencode'` — the custom binary is
silently ignored. Nothing in `behavior.feature` pins whether `{{harness}}` is the
name or the binary, and no test asserts the launched argument equals `Binary`,
which is why the gap is invisible.
**Fix:** decide and encode one contract. Either (a) substitute `{{harness}}` with
the harness *binary* (thread `Harness` through `selectHarness`/`askLaunchCmd`
instead of a bare `name` string), or (b) drop `binary` from the declared-entry
surface if it is meant for detection only, and document that `{{harness}}` is the
display name. Add a test that launches with a name≠binary entry and asserts the
argument that actually reaches the shell.

## Finding 2 — Temp prompt file is orphaned when the launch fails

**Title:** `Execute` writes the prompt file and never removes it if `Launch`
returns an error.
**Why it matters:** bug (resource leak / inconsistent cleanup)
**Where:** `internal/harness/harness.go` `Execute` (~L176–188)
**Evidence:** `Execute` does `promptPath, err := PromptFile(...)` then
`return Launch(...)`. `writePromptFile` deliberately removes the file on a
half-written/close failure, but when `Launch` fails (bad `handoff.cwd`,
`sh -c` spawn error — exactly the case covered by `TestCmdAskSpawnError`) the
fully written file is left behind forever. The "never delete" contract in the
plan is justified because "the harness may read it after tsk exits"; on a failed
launch no harness exists to read it, so this is pure garbage on disk, not a
carrier.
**Fix:** in `Execute`, when `Launch` returns a non-nil error, `os.Remove(promptPath)`
before returning it. Keep the success path untouched.

## Finding 3 — `tsk ask` treats a leading flag as the task id

**Title:** A flag in the id position produces a confusing "invalid id" error.
**Why it matters:** edge case (poor error path for a plausible invocation)
**Where:** `internal/cli/cli.go` `cmdAsk` (L647–652)
**Evidence:** `idStr := args[0]` is taken unconditionally. `tsk ask --harness opencode`
makes `args[0] == "--harness"`, so `parseID` fails with
`invalid id: --harness` rather than a usage message pointing at the missing task
id. The other subcommands guard the shape in `Run` (`len(args) < 2`), `ask` does
not.
**Fix:** reject an id that starts with `-` (or move the `--harness` scan before
taking `args[0]`), emitting the existing `usage: tsk ask <task-id> [--harness NAME]`.

## Finding 4 — Redundant handoff-command validation

**Title:** The `{{prompt_file}}` precondition is validated three times on one call.
**Why it matters:** maintainability (duplication; muddy layering)
**Where:** `internal/cli/cli.go` `cmdAsk` (L669) → `harness.Execute` (L180) →
`harness.Launch` → `harness.ExpandTemplate` (L118)
**Evidence:** `cmdAsk` calls `harness.ValidateCommand` explicitly, then
`harness.Execute` calls it again, then `Launch`→`ExpandTemplate` calls it a third
time. The TUI (`openAskAI`) also calls it before `Execute`. The check is cheap,
so this is not a correctness bug, but the explicit pre-check in `cmdAsk` is dead
work whose only value (ordering the error before opening the DB) is not
exercised by a test.
**Fix:** pick one layer as the owner of the precondition (e.g. `Execute`/`Launch`)
and drop the redundant call, or add a comment stating the pre-check exists purely
to fail fast before `openDB`.

## Finding 5 — Empty-list "unknown harness" message renders a dangling suffix

**Title:** `selectHarness` prints `(available: )` when nothing is available.
**Why it matters:** readability (error message quality)
**Where:** `internal/cli/cli.go` `selectHarness` (L723)
**Evidence:** `fmt.Errorf("unknown harness: %s (available: %s)", want, harnessNames(available))`
with `available == nil` yields `unknown harness: nope (available: )`. The empty
case is handled separately only when `want == ""`; with a `--harness` given and
nothing detected the message is malformed.
**Fix:** special-case the empty list (reuse `harness.NoHarnessesMessage`) or
build the suffix only when `len(available) > 0`.
