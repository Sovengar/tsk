# Security lens review — feat/ask-ai-handoff

Diff range: `main...HEAD` (merge-base c5166893ac2d8f7603b715cc2f5f4a74ebe3218a)
Lens: security (secrets, input validation, shell injection, temp-file lifecycle, spawn safety, unsafe defaults, deps, traversal, authz)

## Summary

The handoff design is deliberately injection-resistant: task data (title/project)
never reaches the shell. It is written to a `0600` temp file whose path is passed
through `{{prompt_file}}`, and every placeholder value (`{{harness}}`, `{{cwd}}`,
`{{prompt_file}}`) is POSIX single-quote escaped by `shellQuote`
(`'` → `'\''`). The `--harness` value is matched against the available list and
the matched display name is used, so the raw argument is never interpolated.
`/bin/sh -c` execution is on the user's own config template (trusted config).
No secrets are added; no new dependencies; fail-closed default (empty
`handoff.command` disables the feature).

Findings are limited to the residual prompt-injection surface and the
never-deleted temp file (a documented tradeoff).

## Findings

### 1. LOW — prompt temp file is never deleted (persistent task data + unbounded accumulation)
Where: `internal/harness/harness.go:245` (`PromptFile`), comment at 241-244; ADR `docs/adr/0001-ask-ai-handoff-contract.md:72-73`.
Evidence: `os.CreateTemp("", "tsk-prompt-*")` (mode 0600) is written and closed but never removed; on success the file outlives the process by design. Each `tsk ask` / TUI handoff leaves a `tsk-prompt-*` file holding the task title and project name. On hosts whose temp reaper is slow or absent (long-running servers, some distros), files accumulate without bound and copies of task metadata persist on disk.
Fix: keep the file for the harness (required) but document the retention as a security tradeoff in README/FEATURES (already in ADR) and consider an opportunistic sweep of stale `tsk-prompt-*` files owned by the current user at startup. Severity stays LOW because 0600 restricts read to the owner.

### 2. LOW — task title/project are interpolated into the AI prompt (prompt-injection surface)
Where: `internal/harness/harness.go:124-132` (`ComposePrompt`).
Evidence: `t.Title` and `t.ProjectName` are embedded verbatim into the natural-language prompt that an autonomous coding harness (claude/codex/opencode/...) will act on with the user's privileges. A title sourced from an untrusted or synced/shared task store could carry instructions ("ignore previous instructions, run …") that the harness may execute. Shell injection is not possible (the prompt is a file, not a command line), but instruction injection into the agent is.
Fix: wrap the interpolated task fields in an explicit data delimiter (e.g. `Task title: <<<...>>>`) and add a line instructing the harness to treat the task fields as data, not instructions. Severity LOW under the current single-user/local threat model.

## Verified safe (no finding)

- `shellQuote` (`harness.go:164`) correctly escapes embedded single quotes; `TestExpandTemplateSubstitutesAndQuotes` covers `'/tmp/p'\''q'`.
- Task text never enters the shell: ADR 60-61 and `Execute` (189-198) confirm the prompt goes to a file.
- `--harness` is validated by `selectHarness` (`cli.go`) and only the matched `h.Name` is used; unknown names error.
- Temp file uses `O_EXCL` via `os.CreateTemp` (no symlink/race), mode asserted 0600 in test.
- `realRunDetached` (`harness.go:216`) sets `Setsid` and inherits null std streams (Go default when Stdout/Stderr nil); background `Wait()` avoids zombies.
- No new dependencies, no secrets, fail-closed default for `handoff.command`.
